# 레거시 모듈 문서화

- 분석 대상 폴더의 파일은 읽기만 한다. 수정 · 이동 · 삭제 · 포맷팅하지 않는다.
- 문서는 한국어로 쓰고 근거는 모두 `파일:줄번호` 로 적는다. 대상 폴더 파일은 그 폴더 기준, 폴더 밖 파일(`db/…`, `docker-compose.yml`)은 저장소 루트 기준 경로다.
- 확인하지 못한 것은 추정으로 채우지 않고 각 문서의 "미확인 목록"에 이유와 함께 남긴다.

## 0. 인자와 산출물

- 첫 인자는 모듈 경로, 둘째 인자는 범위 제한(파일 · 화면 등)이다. 모듈 경로가 없으면 묻고 멈춘다.
- `<모듈명>` 은 폴더 이름이 아니라 아래 표의 이름이다. 표에 없는 경로면 사람에게 묻는다.

| 모듈 경로 | `<모듈명>` |
|---|---|
| `legacy/item-bank-php` | `item-bank` |
| `legacy/assignment-thymeleaf` | `assignment` |
| `legacy/grade-mssql` | `grade` |

- 산출물: `docs/<모듈명>/ARCHITECTURE.md`, `docs/<모듈명>/ERD.md`, `docs/<모듈명>/BUSINESS-RULES.md`. 이미 있으면 덮어쓰기 전에 묻는다.

## 1. 절차

단계가 끝날 때마다 결과를 파일로 저장한 뒤 다음 단계로 넘어간다. 각 문서 머리에 "분석 범위"(끝낸 단계 · 아직 안 한 단계)를 적는다.

1. **계획 제시** — 파일 목록과 줄 수를 모아 읽을 파일 · 단계 · 산출물 · 범위 제한을 짧게 보여 주고, 사람이 확인하면 시작한다.
2. **진입점** — URL · 화면 · main · 스케줄 등 처음 실행되는 파일과 그 뒤 주요 호출 순서를 표로 적는다. → `ARCHITECTURE.md`(모듈 개요 · 폴더 구조 · 진입점) 저장.
3. **의존 관계** — include/import · 함수 호출 · 외부 라이브러리 · 설정을 따라가 mermaid 다이어그램과 표로 적는다. 화살표마다 실제 호출 줄을 근거로 단다. → `ARCHITECTURE.md` 에 의존 관계 · 미확인 목록을 더해 저장.
4. **데이터 흐름** — 스키마 출처(DDL 위치 · 접속 설정)를 먼저 밝히고, 테이블 목록 · 관계(선언 FK 와 코드 JOIN 구분) · 테이블별 읽기 · 쓰기 위치(파일 · 함수 · SQL 요지)를 적는다. 뷰 · 프로시저 정의가 폴더 밖에 있으면 찾아 읽는다. → `ERD.md` 저장.
5. **비즈니스 규칙 후보** — 조건문 · WHERE/ORDER BY · 검증 · 상태 전환 · 숫자 한도에서 규칙을 뽑아 2절 형식으로 적는다. 끝에 "매직 넘버 · 매직 값", "주석만 있거나 주석과 코드가 다른 곳", "같은 규칙을 여러 곳에서 다르게 구현", "없는 규칙 · 미확인" 절을 둔다. → `BUSINESS-RULES.md` 저장.
6. **표본 점검 추천** — 3절대로 답변에 적는다.

## 2. 규칙 형식

~~~markdown
### BR-01
- 규칙: 조건 → 결과 한 문장. 코드가 하는 일만 적는다.
- 근거: `search.php:522`, `db/mariadb/init/01-schema.sql:70`
- 근거 코드:
  ```php
  근거 줄을 그대로 옮긴 1~4줄
  ```
- 확신도: 확실 | 추정 | 미확인
- 비고: 주석과 다른 점, 같은 규칙의 다른 구현, 매직 넘버, 실행 여부. 없으면 —
~~~

- ID 는 `BR-01` 부터 매기고 화면 · 기능별 절로 묶는다.
- 확신도: "확실" = 조건문이나 SQL 로 확인. "추정" = 여러 줄을 이어 추론(비고에 추론 과정). "미확인" = 근거 파일을 읽지 못함. 실행하지 않았으면 비고에 "실행해 보지 않았다"고 적는다.

## 3. 사람이 표본 점검할 규칙 3개 추천

마지막 답변에 표(ID / 규칙 요지 / 확인할 파일:줄번호 / 고른 이유)로 3개를 추천한다.

1. 가장 그럴듯한 규칙 1개 — 당연해 보여서 검토 없이 넘어가기 쉬운 규칙.
2. 주석 · 안내 문구와 코드가 다른 규칙 1개.
3. 여러 줄 · 여러 파일을 이어 추론한 규칙 중 확신도가 가장 낮은 것 1개.

사람의 점검 결과는 `BUSINESS-RULES.md` 끝에 "검증 이력" 절(날짜 · 규칙 ID · 결과 · 틀린 점)로 남긴다.

## 4. 하지 말 것

- 존재하지 않는 함수 · 파일 · 테이블 · 컬럼 이름을 쓰지 않는다. 적기 전에 정의 줄을 찾아 근거로 달고, 못 찾으면 미확인으로 둔다.
- 호출 방향을 거꾸로 적지 않는다. "A → B" 는 A 안에 B 를 부르는 줄이 있을 때만 쓴다. include 관계와 호출 관계를 섞지 않는다.
- 코드에 없는 규칙을 만들지 않는다. 주석 · 안내 문구 · 머리 주석 · 변수 이름에만 있는 내용은 "주석만 있음" 표에 둔다. 주석의 결과 예측(예: "대개 0건")을 규칙 본문에 옮기지 않는다.
- 폴더 밖 정의(뷰 · 스키마 · 프로시저 · collation)를 읽지 않은 채 "~만 나온다", "0건이다"라고 결론 내리지 않는다.
- 같은 줄에서 여러 동작이 갈리면 뭉뚱그리지 않는다(예: 보정마다 경고가 뜨는지, `(int)` 변환이 `3abc` 를 3 으로 만드는지).
- 파일 목록을 추측한 파일명으로 대신하지 않는다. 목록 명령이 실패하면 사람에게 알린다.
- 버그인지 의도인지 판정하지 않는다. 관찰로만 적는다.
